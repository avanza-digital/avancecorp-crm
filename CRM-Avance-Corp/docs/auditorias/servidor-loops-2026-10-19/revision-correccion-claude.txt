FINDINGS:

[P2-1] A JWT-expiry error now silently and permanently stops solicitudes polling for authorized roles
File: `CRM-Avance-Corp/app/src/data/crm-queries.ts` (hunk @@ -967), together with the `crm-api.ts` normalizer (~2743)
Problem: The `enabled` guard disables auto-fetch on `SIN_PERMISO`. The normalizer maps both `42501` and `PGRST301` to `SIN_PERMISO`. In PostgREST, `PGRST301` is a JWT error: an expired or undecodable token, sent as HTTP 401. It is not a policy denial.
Evidence:
- Normalizer: `codigoPg === '42501' || codigoPg === 'PGRST301'` → `code = 'SIN_PERMISO'`.
- Guard: `!['SIN_PERMISO','42501'].includes(codigoDeError(...))`.
- Recovery paths named in the diff comment are explicit `refetch()` or "Auth limpia la caché al cambiar sesión". A successful token refresh is not a session change, so no `AUTH_CLEARED_EVENT` fires.
- In observation mode the panel renders no retry button. Only the `!observacion && q.isError` branch shows "Reintentar condiciones".
Impact (hypothesis on frequency; the mechanism follows from the code shown): A request can race an expired token, for example on laptop wake or tab resume before supabase-js refreshes. After that, a seller or supervisor in observation mode gets a query with no polling, no focus/reconnect refresh, no invalidation refresh and no visible retry. That lasts until gc (5 min with no observers) or logout. Pending-solicitud status in the ficha then stops updating without any notice. Before this diff, the next poll or focus event would have recovered.
Recommendation: Make the stop condition specific to a real authorization denial. Options:
- (a) Have the normalizer keep the original `codigoPg` or HTTP status on `CrmApiError` and stop only on 42501/403.
- (b) Exclude `PGRST301` by checking status 401 vs 403 if `CrmApiError` already carries it.
Add one unit case asserting that a `PGRST301`/401 error does not disable auto-refetch.

[P2-2] `retryOnMount: false` changes behaviour for every consumer of `useSolicitudesTasa`, not only the lead panel
File: `CRM-Avance-Corp/app/src/data/crm-queries.ts` (same hunk)
Problem: `useSolicitudesTasa` is the shared Rentabilidad hook. Its docstring and the `refrescarCadaMs`/`opciones` parameters point to other consumers, such as the approval tray and notifications. The `enabled` guard is reasonable for all of them, because a 403 should never poll. `retryOnMount: false`, however, also suppresses the mount-time retry after transient errors such as NETWORK_ERROR or 5xx.
Evidence: In TanStack v5, `shouldLoadOnMount` skips fetching when `status === 'error' && retryOnMount === false` and there is no data. The option is set unconditionally in the hook.
Impact: Consider a screen that does not poll and has no retry button. Before this change, navigating away and back after a transient failure recovered automatically. Now it keeps the error until focus, reconnect or gc. That is a quiet regression outside the stated scope ("fix the lead panel loop").
Recommendation: Do one of the following:
- Confirm that every `useSolicitudesTasa` call site either polls or renders an explicit retry, and record that list.
- Pass `retryOnMount` through `OpcionesSolicitudesTasa` and set it only from `CondicionesTasaLeadPanel`/`SolicitudTasaLeadPlegable`.

Either way keeps the loop fix, because the shared key's parent and child both come from that panel.

[P3-1] The query-cache assertion in the drawer tests may be vacuous
File: `CRM-Avance-Corp/app/src/components/app/lead-drawer-datos.test.tsx` (new `describe('Ficha · lectura de condiciones de tasa')`)
Problem: `q.queryKey.includes('solicitudes')` is an exact-element match on the array. If `crmQueryKeys.solicitudesTasa` yields something like `['crm','rentabilidad','solicitudes-tasa',…]`, the filter never matches and `toHaveLength(0)` passes no matter what.
Evidence: The key shape is not included in the evidence. The consultas test invalidates through `crmQueryKeys.rentabilidad()` as a prefix, so the actual segment name is unconfirmed.
Recommendation: Either:
- match the prefix with `crmQueryKeys.solicitudesTasa(...)` via `partialMatchKey` or `queryCache.findAll({ queryKey: … })`, or
- assert directly that the mocked `listarSolicitudesTasa` was never called.

Check it once against original main: the cache assertion on its own should fail there.

[P3-2] Some E2E call counts are read synchronously, so they can miss late requests
File: `CRM-Avance-Corp/app/e2e/tasa-lead-sin-bucle.spec.ts`
Problem: `expect(consultas).toBe(0)` and `toBe(1)` run right after `page.clock.fastForward(...)` or an action, with nothing waiting for network idle. An in-flight extra request could land after the assertion. For the "0 calls" and "still 1 call" checks, that race makes the test pass.
Recommendation: Before counting, wait for a deterministic UI settle, or run `page.waitForLoadState('networkidle')` and a short real-time drain. Alternatively, assert with `expect.poll(() => consultas)` over a bounded window that the count stays fixed.

[P3-3] The docstring lost its polling semantics
File: `crm-queries.ts`, docstring of `useSolicitudesTasa`
Problem: The old text said "Se refresca solo mientras hay pendientes que esperar", which described what `refrescarCadaMs` is for. The new docstring only describes the 403 behaviour.
Recommendation: Keep both sentences.
