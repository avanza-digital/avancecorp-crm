FINDINGS:

[P2] Deadlock window between the `intentos>=8` sweep and the `invalidos` claim
File: supabase/migrations/20260910225540_crm_notificaciones_push_tasa.sql
Lines: 187-200
Problem: The `invalidos` CTE uses `order by e.id ... for update skip locked`, but the immediately following sweep (198-200) is an unordered, unbounded `UPDATE` with neither `skip locked` nor `limit`.
Evidence: Both statements target the same predicate space (`estado in ('pendiente','enviando')` and an expired/absent lease). Worker A can hold row X from `invalidos` (B skipped it) while its sweep blocks on row Y held by B's `invalidos`; B's sweep blocks on X. A row that is both lease-expired and device-invalid with `intentos=8` satisfies both sets.
Impact: Periodic `deadlock detected` aborts of the whole cron pass; the reported concurrency tests (disjoint claims, disable vs 410) do not cover this pair.
Recommendation: Fold the sweep into the `invalidos` CTE, or give it `order by id ... for update skip locked limit 100` with the same ordering discipline used elsewhere.

[P2] `push` event can settle without showing a notification
File: app/public/sw-crm.js
Lines: 12-29
Problem: Any rejection inside the chain (`caches.open` in a storage-restricted context, a corrupt `/__crm_push_recibidos` body failing `.json()`) is swallowed by `entregaPendiente.catch(() => {})` on the *next* push, so the current event resolves with no `showNotification()`. The deliberate `return` at line 15 when `interruptor !== '1'` has the same shape.
Evidence: Line 15 returns before `showNotification`; line 17 `await registro.json()` is unguarded; the only recovery is the `catch(() => {})` at line 12, which does not display anything.
Impact: `userVisibleOnly: true` is violated. Chrome surfaces "This site has been updated in the background" and, after repeated violations, may drop the subscription. This is most likely on the path the design relies on — a phone whose logout revocation failed keeps receiving queued sends with `interruptor=false`.
Recommendation: Wrap the cache/dedupe reads in try/catch and fall back to showing the generic notice; for the intentional suppression path, make the queue drain faster (see next finding) so the suppression window is short, and document the accepted violation budget.

[P2] Orphan revocations retry only from the config screen
File: app/src/lib/notificaciones-tasa.ts
Lines: 37-45, 73-76
Problem: `reintentarRevocaciones()` is called exclusively from `consultarPushTasa()`.
Evidence: No other call site in the attached file; `vincularCuentaPushTasa` (61-67) does not invoke it on login.
Impact: A device whose logout RPC failed stays `activo` server-side until its owner happens to reopen Configuración. Meanwhile every new request enqueues a send that is delivered and silently dropped, compounding the `userVisibleOnly` issue above.
Recommendation: Also drain pending revocations once on successful sign-in for the matching account.

[P2] `revoke select on net.http_request_queue` may succeed as a no-op (deployment-dependent)
File: supabase/migrations/20260910225540_crm_notificaciones_push_tasa.sql
Line: 323
Problem: On managed Supabase, `net` objects are owned by `supabase_admin`. A `REVOKE` issued by a role without grant option emits a warning, not an error.
Evidence: PRIMARY's own production read shows `has_table_privilege(... SELECT)=true` for all three API roles today; the migration has no post-condition asserting the revoke landed.
Impact: The migration can report success while `authenticated`/`anon` retain `SELECT` on rows that transiently hold `x-cron-secret` (lines 300-303).
Recommendation: Follow the revoke with an assertion in the same transaction (`do $$ begin if has_table_privilege('authenticated','net.http_request_queue','SELECT') then raise exception ...`). Note `net` is unexposed to PostgREST, so this is defence-in-depth, not a live leak.

[P3] `WindowClient.navigate()` retargets an arbitrary same-origin window
File: app/public/sw-crm.js
Lines: 37-45
Evidence: `ventanas.find(...)` picks the first same-origin client, not the focused one, and navigates it unconditionally.
Impact: A tap can navigate away from an in-progress form in another tab.
Recommendation: Focus first and prefer `postMessage` routing, falling back to `navigate()` only when no client responds.
