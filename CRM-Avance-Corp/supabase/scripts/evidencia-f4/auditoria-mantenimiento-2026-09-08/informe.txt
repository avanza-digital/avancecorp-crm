SUMMARY:
The minimal fix is correct for the defect it targets. `LOCK TABLE crm.backfill_multiempresa_mapa IN SHARE MODE NOWAIT` is the right instrument for a phantom (absent-row) hazard that `FOR UPDATE` cannot cover, it is placed correctly (after the idempotent replay return, before the first census validation), it cannot introduce a wait cycle because the batch never blocks on it, and the before/after evidence is unusually clean: the FAIL artifact carries `md5Funcion=81f9115…` and the PASS artifact `a33595d…`, so the two artifacts genuinely bracket a body change.

The problem is scope, not correctness. The attached body of `private.backfill_multiempresa_ejecutar` — the legacy F2 path whose non-participation in the identity flags caused this bug — writes **four** distinct census inputs, of which the fix now guards one. The same absent-row race the primary just reproduced against `crm.backfill_multiempresa_mapa` is reachable, by the same writer, against `crm.inversiones` / `crm.inversion_titulares` and `crm.inversionista_identificadores`. Whether that produces a clean 23505 abort or a duplicated financial row depends on unique constraints that are not in the attached evidence.

FINDINGS:

**[P1] The phantom guard closes one of four census inputs written by the same unguarded legacy path**

File:
`CRM-Avance-Corp/supabase/scripts/f4/08-historicos-lote.sql`, `CRM-Avance-Corp/supabase/scripts/f4/07-historicos.sql`

Lines:
`08-historicos-lote.sql:119`, `08-historicos-lote.sql:132-145`; `07-historicos.sql:64`, `07-historicos.sql:97`, `07-historicos.sql:115-118`, `07-historicos.sql:123-128`

Problem:
`v_inversiones := array_agg(distinct (value->>'inversion')::uuid)` is `{NULL}` for every `pendiente` source, so lines 143-144 lock nothing. `crm.inversionista_identificadores` is never locked at all. Both are absent-row cases — exactly the class the new `SHARE` lock exists to cover for the mapa.

Evidence:
The attached live body of `private.backfill_multiempresa_ejecutar` writes, in one transaction and without any advisory flag lock:
- `crm.backfill_multiempresa_mapa` via `private.f2_mapear` — now guarded;
- `crm.inversionistas` and `crm.inversionista_identificadores` via `private.inversionista_resolver(r.tipo, r.dnorm, true, 'backfill-A'|'backfill-B')` with create=true — **unguarded**;
- `insert into crm.inversiones (…) where not exists (select 1 from crm.inversiones inv where inv.cierre_externo_id = r.id)` and the matching `crm.inversion_titulares` insert — **unguarded for the absent-row case**.

The `cierres_externos` row lock does not cover this. In class B the executor runs `update crm.cierres_externos set inversionista_id = v_inv where id = r.id and inversionista_id is null`; when `inversionista_id` is already set the UPDATE matches zero rows and acquires **no** row lock, then proceeds to `insert into crm.inversiones`. That state — cierre with `inversionista_id` set, no inversion row — is precisely `estado='pendiente'` in the census (`07-historicos.sql:97`, `129`), i.e. an accepted batch input.

The census re-reads at `07-historicos.sql:64/97` use `select … into v_inv`, which silently takes an arbitrary row if two inversions exist for the same source, so the post-link reconciliation at `08-historicos-lote.sql:174-177` is not a reliable backstop.

Impact:
An uncommitted concurrent F2 insert is invisible to both census passes and unblocked by every lock the function takes. If `crm.inversiones` has no unique constraint on `cierre_externo_id`/`contrato_id`, the outcome is two inversion rows for one source — a duplicated financial record, strictly worse than the mapa defect just fixed. If the constraint exists, the outcome is a bounded wait then 23505 and a clean rollback, which is acceptable but currently undocumented and untested.

Recommendation:
1. Establish the constraint facts first: `\d crm.inversiones` / `\d crm.inversion_titulares` (unique on `cierre_externo_id`, on `contrato_id`, and on `(inversion_id, rol='principal')`).
2. If the uniqueness holds, this reduces to documentation plus a test; state the 23505 path explicitly in the runbook.
3. If it does not, extend the guard symmetrically — `lock table crm.inversiones, crm.inversion_titulares, crm.inversionista_identificadores in share mode nowait` alongside line 119. This is cheap here specifically because the function already requires `inversiones_escritura` OFF (`08-historicos-lote.sql:101-103`), and `probar-historicos-limite.mjs` demonstrates that 100 real `crm.convertir_lead_externo` calls with F4 OFF produce zero inversion rows — so the only writer excluded by that lock is the legacy F2 maintenance you are already trying to exclude.

**[P3] Caller `statement_timeout` pre-empts the function's `lock_timeout`; the 5 s is per-wait, not per-transaction**

File:
`08-historicos-lote.sql:50`; `probar-historicos-limite.mjs:50`

Evidence:
The function sets `lock_timeout='5s'`; the limit harness sets `statement_timeout='4s'` on the outer statement. Under that caller, a real lock wait is cancelled at 4 s with 57014, not 55P03/40001. Conversely, `lock_timeout` bounds each individual wait, so a 100-source batch that contends repeatedly in the write loop (FK key-share on `crm.empresas`, unique-index waits) has a worst case of many multiples of 5 s, unbounded by the function itself.

Impact:
Retry logic or runbooks keyed only on 55P03/40001 will not recognise 57014. Not a correctness defect.

Recommendation:
Document the intended caller budget, and state that the transaction-level bound is the caller's `statement_timeout`, not `lock_timeout`.

TEST GAPS:
- No test mirroring `probar-historicos-mantenimiento.mjs` with an uncommitted `insert into crm.inversiones` (or `crm.inversion_titulares`, or `crm.inversionista_identificadores`) for a source the batch will link — the direct analogue of the P1 finding, and the cheapest way to settle it.
- No `DELETE` on the mapa in the concurrency matrix; only INSERT (line 39) and ON CONFLICT UPDATE (line 59) are covered. `SHARE` conflicts with `ROW EXCLUSIVE` so this should pass, but it is untested.
- No test that a full `private.backfill_multiempresa_ejecutar` in progress deterministically rejects the batch. That executor holds ROW EXCLUSIVE on the mapa for its entire run, so the batch can never start while it runs — correct-by-design fail-fast, but it deserves an explicit test and a runbook line, since the operator-facing message is the generic `could not obtain lock`.
- No test that the advisory waits at lines 96-97 are bounded. Both are unconditional `pg_advisory_xact_lock` (waiting, not `_try`); a stalled administrative session holding `crm_flag_resolver_en_puertas` blocks the batch. I have not verified from the attached evidence that `lock_timeout` bounds advisory-lock waits — treat that as a hypothesis and test it rather than assume it.
- No batch-vs-batch test (same `p_lote` and different `p_lote` concurrently). The advisory locks should serialise them; `SHARE` is self-compatible, so the mapa lock contributes nothing to batch-vs-batch exclusion — worth stating, because the code comment at lines 117-118 ("NOWAIT rechaza otra intervención administrativa") reads as if the table lock provides that exclusion when in fact the advisory locks do.

ARCHITECTURE RISKS:
- The function's real invariant is "every input the census reads is either locked or provably immutable for the transaction". That invariant is currently enforced input-by-input and re-derived by hand at each iteration; this review found the same class recurring in a sibling table one commit after it was fixed in the first. Consider expressing it once — an explicit, commented list of census inputs mapped to the lock that covers each, and a structural test that fails when the census reads a relation not on that list.
- Duplicated function bodies across `scripts/f4/*.sql` and the candidate migration (see P2).

SECURITY RISKS:
- No new surface. `SECURITY INVOKER`, the `session_user`/`current_user` gate at lines 72-74 and the REVOKEs are intact; the `crm.op_privilegiada` window at lines 160-164 is correctly narrowed to the single UPDATE and does not span `inversion_vincular_fuente`. The `when others` handler at 188-190 only restores a transaction-local GUC that a rollback would restore anyway — harmless, and it re-raises rather than swallowing.
- One deployment check: `LOCK TABLE … IN SHARE MODE` requires UPDATE/DELETE/TRUNCATE (or MAINTAIN) on the relation, a privilege `ACCESS SHARE` did not require. It works in the bank, but the bank is a `pg_dump`/`pg_restore` copy; confirm `postgres` holds it on `crm.backfill_multiempresa_mapa` in the real target, otherwise the first production run fails 42501 at line 119.

REGRESSION RISKS:
- The table-level `SHARE` blocks every writer of `crm.backfill_multiempresa_mapa` for the batch duration (~93 ms measured, uncontended, 100 sources). Confirm the writer set is limited to `private.f2_mapear` callers and contains no request-path function; the attached evidence is consistent with that (mapa count is 0 after `cargarHistoricosPrueba`, and the mapa snapshot is inside the invariance check at `probar-historicos-limite.mjs:77-80`) but does not enumerate writers exhaustively.
- Deadlock exposure is low and correctly bounded: every lock the batch takes explicitly is NOWAIT, so the batch cannot participate in a cycle through them. Residual cycles remain possible through implicit locks in the write loop (FK key-share on `crm.empresas`, unique-index waits) while the batch holds the mapa `SHARE`; the deadlock detector resolves them and the acta is written in the same transaction, so any abort is atomic. Acceptable.
