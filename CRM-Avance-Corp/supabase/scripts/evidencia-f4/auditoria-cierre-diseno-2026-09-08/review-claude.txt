VERDICT:
CHANGES_REQUESTED

SUMMARY:
Both contracts are directionally sound — neutral provenance as a separate immutable table, and payload correction as append-only revisions with an optimistic version — but each has at least one concrete defect that is visible in the attached evidence, not a stylistic preference. For (A), the proposed call site cannot satisfy the proposed schema: `inversion_id` does not exist yet at line 124 of `crm.crear_contrato_con_cuenta_pdf_v2`, and that call site is silently skipped on the writer's idempotent replay branch. For (B), the correction contract collides with two existing confirm-time invariants: `analista_cierre_id` is validated at confirm against the *initial* responsible (02-confirmacion.sql:162-172) while `preparar` validates against the *current* one (01-base.sql:387-389), and a legacy `confirmar_inversion_fn(uuid)` wrapper hard-coding expected revision 0 breaks the already-confirmed retry path (02-confirmacion.sql:97-107) for any corrected solicitud. Also, the RESTRICT FK plus immutability trigger makes the existing authorized contract-deletion path (`private.proteger_titulares_documentales` lines 6-10) unexecutable.

`unique contrato_titular_id FK public.contrato_titulares RESTRICT` combined with "UPDATE/DELETE prohibited by immutable trigger" makes the authorized deletion of `contrato_titulares` rows impossible once provenance exists.

[P1] Correction of `analista_cierre_id` creates a permanently unconfirmable solicitud

File:

Lines:
01-base.sql:387-390; 02-confirmacion.sql:162-176

The two existing validations of `contrato.analista_cierre_id` use different reference values. `preparar` compares against the *current* responsible; `confirmar` compares against the *initial* responsible reconstructed from the first review row. If the extracted `private.inversion_validar_datos` is reused verbatim by the correction RPC, a payload that passes correction can be rejected forever at confirm.

Evidence:
`01-base.sql:387-389`
```

   and p_datos#>>'{contrato,analista_cierre_id}' is distinct from v_ctx->>'responsable_id' then
```

Problem:
The proposal keeps `crm.confirmar_inversion_fn(uuid)` as a wrapper passing expected revision 0, and states "confirmed replay must match revision". The existing function's confirmed-replay branch is a pure read that returns the stored result; gating it on a version check converts a successful retry into a hard error.

Evidence:

[P2] `NOWAIT` lock failure must not abort the financial confirmation

File:

Lines:

Problem:
The proposal takes a non-blocking advisory lock plus `FOR UPDATE NOWAIT` on cotitular persons late in the confirm transaction. Fusion acquires person locks early (line 35) and inversion/titular locks late (56-60); confirm acquires solicitud first (93) and person locks last. TEST GAPS:

- Provenance survives F3 fusion of the cotitular: link, fuse cotitular into a canonical identity, assert the origen row still exists, its `persona_origen_id` is unchanged, and the reader resolves to the canonical person. Same for fusion of the *principal*.
- Authorized contract deletion with provenance present: exercise the `crm.contrato_pdf_eliminacion_autorizada` path end-to-end and assert the designed 55000/success, not 23503.
- Direct `update` and `delete` as `postgres` on both new tables must raise (guards against the `f4_fuente_inmutable` hard-coded-list trap).
- Idempotent confirm retry **after** a correction, through both the new RPC and the legacy `confirmar_inversion_fn(uuid)` wrapper: both must return `reintento=true` with the stored result, never 40001.
- Correction replay: same `p_clave_correccion` + same arguments returns the receipt after the revision has advanced; differing arguments returns conflict; differing `p_motivo` alone returns conflict, not a stale receipt.
- `preparar(clave, original_datos)` after a correction: must still return the stored state (no P0409) and must report the current hash and `revision_datos`, not the original.
- Correction attempted in each non-`preparada` state (`confirmada`, `cancelada`) and with a stale `revision_datos` → rejected.
- Correction attempted after `auth_claim_id` exists with an `alta_portal` change → rejected; without touching `alta_portal` → allowed.
- Correction then confirm on the Avance branch, asserting the 02-confirmacion.sql:169-171 `analista_cierre_id` check still passes (this is the [P1] cross-check).
- Concurrency: confirm-with-cotitular racing a Gerencia fusion of that cotitular — assert the confirmation commits and the cotitular is left pending, not that the confirmation aborts.
- Two concurrent corrections on the same solicitud with different keys → exactly one applies, the other gets 40001 (not 23505).
- Ambiguity: a document resolving to two canonical owners across current and historical identifier rows → stays pending, no origen row, contract still recorded.
- Duplicate source rows with the same document → two origen rows, one membership pair, principal role preserved (per the stated contract).
- Storage: assert no correction path can leave an object in `f4-comprobantes` that is unreferenced by `datos#>>'{evidencia,ruta}'`.
- Authorization matrix for the correction RPC: `anon`, `authenticated` without `puede_gestionar_contratos_crm`, and a responsible for a different person — all rejected; plus `revoke`/`grant` assertions matching the pattern at 01-base.sql:397-398.

ARCHITECTURE RISKS:

- Placing F4 provenance inside `crm.crear_contrato_con_cuenta_pdf_v2` makes a general-purpose contract writer carry investment-domain semantics and inherits its idempotency replay branch. Confirm-side placement keeps the layering intact.
- Two independent version counters (`inversion_solicitud_revisiones.revision` and `revision_datos`) with the same starting value and near-identical parameter names is a durable misuse hazard for every future caller.
- Provenance that FKs into three mutable identity/contract tables while claiming immutability is fragile; snapshot columns make it self-contained and reduce coupling to F3.

SECURITY RISKS:

- Correction RPC granted at `preparar` authorization level would let a principal rewrite financial terms of a pending investment ([P1] above).
- `source_sha256` as a document-confirmation oracle if ever exposed ([P2] above).
