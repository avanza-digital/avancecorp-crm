File:

- `private.registrar_ajuste_si_mes_cerrado` (1253, 1735)

- `private.contratos_afectados_por_anulacion` (1245, 1454, 1458)

- `private.leads_de_identidades`, `private.leads_de_personas` (1341, 3080, 3087)

That you *had* to adapt `private.cierre_anulado` (989–1005) is direct evidence this class of bug is live: without `and ce.es_cierre_inicial`, annulling a *non-initial* F4 investment would have marked the lead's original conversion as annulled. Recommendation:
Add a mechanical inventory step, not a judgement call: enumerate every `pg_proc` whose `prosrc` matches `cierres_externos` (and every view/policy), and assert each is either (a) in the md5 guard list *and* adapted, or (b) recorded in an explicit `no_requiere_adaptacion` allowlist with a one-line reason. Fail the migration if the set is non-empty and unclassified. Do the same for `crm.inversiones` before any consumer starts reading `inversiones.estado` (see P3-b).

**[P1] `fecha_comercial` has no lower bound: an in-scope vendedor can retro-date capital into any month that was never sealed**

File:
`CRM-Avance-Corp/supabase/migrations/20260907191832_crm_f4_inversiones_base_y_escritores.sql`

Lines:
4918–4921 (`inversion_validar_datos`), 592–599 (`confirmar_inversion_revisada_fn`), 92–99 (`cierres_f4_fechas_validas`)

Problem:
The only temporal guards on `fecha_comercial` are `isfinite()` and *not in the future*:

```sql
if v_fecha is null or not isfinite(v_fecha) or v_fecha>(statement_timestamp() at time zone 'America/Lima')::date
   or v_vence is null or not isfinite(v_vence) or v_vence<=v_fecha then
```

and the table CHECK only enforces `fecha_comercial <= fecha_imputacion <= creado_en::date`. The sealed-period path (596–606) is the *sole* protection, and it only fires when `crm.periodos_cerrados` has a row for `date_trunc('month', fecha_comercial)`.

Evidence:
`private.capital_episodios` now windows cooperativa rows by `coalesce(fecha_imputacion…, creado_en)` (968–985). When the origin month is unsealed, `v_ajuste` is false and `v_imputacion := v_fecha` (599) — so the row lands in that historical month. `crm.corregir_solicitud_inversion_fn` also permits moving `fecha_comercial` freely (it is not in the frozen-fields list at 5034–5042), re-validated only by the same unbounded `inversion_validar_datos`.

Impact:
Any month that was never sealed — every month before sealing was introduced, plus any gap month — accepts new capital dated into it. This is not merely a reporting artifact: it moves the monthly capital aggregate that `cierres_externos_fn.por_empresa` (2113) and, per your own comment at 2093–2096, `cumplimiento_metas_fn`'s `capital_real` are built from. This is the commission basis. A vendedor in scope, not Gerencia, can do it.

Recommendation:
Bound `fecha_comercial` in `inversion_validar_datos`: current month, or `>= now() - N days`, with anything older routed through an explicit Gerencia-authorized path that always produces an `inversion_ajustes_mes_cerrado`-style trace regardless of seal state. Alternatively, make *any* `fecha_comercial` outside the open month produce an ajuste row even when the month is unsealed, so the retro-dating is at least append-only and visible.

**[P2] The phone-visibility fix regresses rows whose canonical person has no current responsable**

File:
migration lines 1970–1978 and 2030–2038 (`crm.cierres_externos_fn`)

Problem:
The new rule replaces `l.vendedor_id = any(v_visibles)` with an `exists` on `inversionistas.responsable_relacion_id`. When the canonical person's `responsable_relacion_id` is `NULL`, the `exists` returns false and the phone is masked — even for the vendedor who legitimately owns the closure snapshot and never lost the relationship.

`private.backfill_multiempresa_ejecutar` only sets `responsable_relacion_id` when `r.vendedor_id is not null` **and** there is no open `inversionista_responsables` tramo (812–818, 772–779). when ce.inversionista_id is not null and exists (
```sql
       select 1 from crm.inversionistas ip

         and ip.responsable_relacion_id is not null)

else l.vendedor_id=any(v_visibles) end
```

**[P2] Provenance permanently freezes `public.contrato_titulares`, including the wholesale `_sync` path**

File:
migration lines 4723–4741

Problem:
`private.f4_proteger_origen_cotitular` raises `55000` on any UPDATE or DELETE of a `public.contrato_titulares` row that has an `inversion_cotitular_origenes` record. It is attached unconditionally (`trg_titular_procedencia_inmutable`), so it survives turning the F4 flag off.

Evidence:
`probar-cotitulares-neutrales.mjs:68–76` confirms both UPDATE and DELETE raise `55000` even under `crm.op_privilegiada='on'`. The migration's own comment (4666–4668) states the helper is called by *"Crear/actualizar contrato"* — implying an update path exists that replaces titulares wholesale.

Impact:
Provenance is recorded only for titulares whose document resolves to a verified identity, so within one contract some rows are frozen and some are not. A `_sync_contrato_titulares` that deletes-and-reinserts will abort on the first frozen row, taking the entire contract update with it. Correcting a typo in a cotitular's name becomes impossible with no supported remediation path.

Recommendation:
Freeze only the *identity-bearing* columns (`tipo_documento`, `documento`) rather than the whole row, and allow DELETE when the corresponding `inversion_cotitular_origenes` row is also being retired through an explicit Gerencia RPC. Alternatively snapshot the document into `inversion_cotitular_origenes` (you already store `fuente_snapshot`) and drop the freeze on `public.contrato_titulares` entirely — the snapshot is what makes provenance durable, not the source row.

**[P2] Read-only RPCs acquire `FOR UPDATE` on `crm.inversionistas`**

File:
migration lines 203–246 (`inversion_persona_autorizada`, `select * into v_i … for update` at 228), 4837–4850, 4979–4991

Problem:
`crm.inversion_cotitulares_fn` and `crm.solicitud_inversion_fn` are pure reads that call `inversion_persona_autorizada`, which takes a row-level write lock on the person plus `identidad_bloquear_documentos_de`, held to commit.

Impact:
Two concurrent UI reads of the same person serialize; a read also blocks (or is blocked by, with the 5 s `lock_timeout`) a concurrent correction, fusion or reassignment. This will surface as sporadic 5 s timeouts in F5, not as a correctness bug, which makes it expensive to diagnose later.

Recommendation:
Split a `private.inversion_persona_autorizada_lectura(uuid)` that performs the identical authorization and canonical resolution with `FOR SHARE` (or no row lock), and use it from the two read RPCs. Keep `FOR UPDATE` on the write paths.

**[P2] `crm-inversion-portal` edge: wildcard CORS and raw server-error passthrough**

File:
`_supabase_functions/functions/crm-inversion-portal/handler.mjs` lines 5–10, 54–58, 121–127

Problem:
(a) `'Access-Control-Allow-Origin': '*'` on a function that holds `SUPABASE_SERVICE_ROLE_KEY` and creates Auth users. Every other edge in this repo uses an allowlist — compare `crm-contrato-pdf-v2/handler.ts:114–151` (`ORIGENES_PRODUCCION` + `Vary: Origin`).

(b) Error passthrough:
```js
error.status = crm ? statusDeErrorSaga(error) : (…);
…
return respuesta(error.status ?? 503, {
  error: error.status ? error.message : 'No se pudo completar el acceso…',
```
`statusDeErrorSaga` **always** returns a number (500 for unmapped codes), so `error.status` is always truthy for RPC failures and `error.message` is always returned verbatim. Any SQLSTATE outside the mapped set (`23505`, `23514`, `55P03`, `P0001`, `no_data_found` from a `SELECT … INTO STRICT`) leaks the raw PostgreSQL message — constraint names, column names, row detail.

Recommendation:
Adopt the `crm-contrato-pdf-v2` origin allowlist, and return `error.message` only for the codes `statusDeErrorSaga` explicitly recognises as business-facing (`P0409`, `P0429`, `22023`, `P0002`, `42501`); everything else → generic text + server-side log.

**[P2] Deployment: ACCESS EXCLUSIVE on `storage.objects` under a 5 s `lock_timeout`, plus an FK into a vendor-managed schema**

File:
migration lines 4–5, 73, 436–437, 707–718

Problem:
`set local lock_timeout='5s'` applies to a transaction that (a) adds `comprobante_objeto_id uuid references storage.objects(id)` and (b) creates six policies on `storage.objects` — each requiring ACCESS EXCLUSIVE on that table.

Impact:
Under production Storage traffic the migration will very likely time out and roll back the whole 5 000-line transaction, and while it holds the lock it stalls every Storage operation. Recommendation:
Document a maintenance window and a retry policy for the apply step. Consider replacing the FK with a recorded `(bucket, path, sha256/etag)` triple plus the restrictive delete policy you already have (717–718), which achieves byte preservation without coupling a business table to a vendor-managed one.

- (a) `crm.inversiones.estado` is set to `'anulada'` by `f4_sincronizar_cierre` (3902–3919) while `capital_episodios` deliberately keeps annulled cooperativa capital as `'stock'` (957–975, ATR-4). - (e) The `do $cotitular_acl$` self-verification block (4685–4697) is an excellent pattern — it asserts the REVOKE actually took effect rather than trusting a possible WARNING. - (g) `inversion_cotitulares_vincular` swallows `deadlock_detected` (4825) alongside `lock_not_available`, degrading to `identidad_ocupada`. Legal, but it will mask a genuine lock-ordering defect. Log or distinguish it.
- (h) Missing-solicitud error codes are inconsistent: `solicitud_inversion_fn` and `confirmar_inversion_revisada_fn` raise `P0002`, while `acceso_inversion_fn` (4001) and `revisar_solicitud_inversion_fn` (4212) omit the `found` check and surface `42501` from the person lookup instead.
- (i) `crm.inversion_ajustes_mes_cerrado.periodo_origen references crm.periodos_cerrados(periodo)` (156) with no `ON DELETE` — if a period-reopen path exists, this makes it impossible once an ajuste is recorded.

ARCHITECTURE RISKS:
- The md5 guard set is an allowlist, not a derived closure — it pins what you remembered to pin. Same structural weakness as the ACL block being applied to one function.
- Two authoritative representations of an annulled cooperativa investment (`inversiones.estado` vs `capital_episodios` measure) will diverge in F5 unless the contract is written down now.
- F2's global backfill is retired at install time, not enable time, and its replacement is bounded at 100 sources per manually-curated lote. Reconciliation capacity after a restore is materially lower than before.
- FK from a business table into Supabase's `storage.objects`.

SECURITY RISKS:
- Wildcard CORS + verbatim error passthrough on the service-key-holding edge (P2).
- Third-party identity binding via cotitulares — impact unverifiable without the RLS on `crm.inversiones` / `crm.inversion_titulares` (P2). This is the one gap I would most like closed before G4.

ON THE PDF WORKER QUESTION (asked explicitly; **not** a pass — the dense run did not pass):

My assessment is that **no implementation change is warranted for recoverability**. The invariants in `crm-contrato-pdf-v2/handler.ts` already hold under an abrupt worker death:
- render precedes upload (1015–1050); upload is `upsert:false` (storage.ts:111) and a conflict is tolerated, never overwritten (`esConflictoObjeto`, 1085);
- on a retry the possibly-orphaned object is downloaded and its SHA-256/bytes compared against the deterministic render, and a mismatch produces `INTEGRIDAD_OBJETO_DIVERGENTE` → 409 (1114–1133) — **no success on integrity mismatch**, confirmed;
- the `intentos > 1` gate on the recovery download (1057) is not load-bearing: if `intentos` is still 1 the code falls through to `subir` → conflict tolerated → download → verify, reaching the same check;
- `lease_expira_en` / `reintentable` are surfaced to the caller, so the user-visible retry story is intact.

The one code-side item I would change is a tunable, not a fix: `p_lease_segundos: 120` is hardcoded (921). If the platform terminates a worker on a CPU budget shorter than 120 s wall-clock, every kill costs a fixed 120 s of unavailability for that contract. Derive the lease from the worker's actual remaining budget, or shorten it and let a live worker renew. Everything else about the observed `WORKER_LIMIT` / CPU-hard-limit failures reads as environmental (render cost per invocation on a `oneshot` request policy), not as a defect in this handler.
