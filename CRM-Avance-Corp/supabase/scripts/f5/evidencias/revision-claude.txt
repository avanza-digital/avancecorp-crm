[P1] Lock errors from the write-path probe abort the whole read-only ficha

File:
`CRM-Avance-Corp/supabase/scripts/f5/01-lecturas.sql`

Lines:
267–275 (specifically 269 and the handler at 271–272)

Problem:
`inversionista_ficha_fn` calls `private.inversion_persona_contexto(v_id)` purely to compute a capability flag, but that function takes real locks and can raise SQLSTATEs the handler does not catch.

Evidence:
Attached published SQL for `private.inversion_persona_contexto` shows `SET lock_timeout TO '5s'`, `select * into v_i from crm.inversionistas where id=v_persona for update;` and `select * into v_l from crm.leads where id=v_leads[1] for share nowait;`.
The handler at `01-lecturas.sql:271-272` catches only `sqlstate 'P0409'`, `sqlstate 'P0429'` and `insufficient_privilege`.
`FOR SHARE NOWAIT` raises `55P03 lock_not_available` **immediately** on any conflicting lock; `lock_timeout` raises the same code after 5 s. `40P01 deadlock_detected` is likewise uncaught.

Impact:
A concurrent edit of the person's lead — an ordinary CRM operation — makes the entire ficha read fail rather than degrading `nueva_inversion` to `false`. The client surfaces a generic error (`inversion-nueva.tsx:88`, `inversionista-ficha.tsx:113`) because the code is not `42501`. On the success path the `FOR UPDATE` row lock on `crm.inversionistas` is held for the remainder of the RPC, which includes three full scans of `cartera_f5_fuentes()` (see the perf finding below), so read traffic serializes against F4 writers. `inversionistas-queries.ts:17` sets `refetchInterval: 15_000`, so every open ficha re-acquires this write lock four times per minute.

Recommendation:
Add `when lock_not_available or deadlock_detected then v_operable := false; v_motivo := '<retry message>';` to the same block. Better: introduce a read-only sibling of `inversion_persona_contexto` that performs the identical validations without `for update` / `for share nowait`, and reserve the locking version for the actual write path. Add a bank test that holds `select ... from crm.leads where id=... for update` in one session and asserts the ficha still returns with `nueva_inversion=false`.

[P1] Read-audit amplification: polling turns `cartera_lecturas` into an unbounded write stream

File:
`CRM-Avance-Corp/supabase/scripts/f5/01-lecturas.sql`, `CRM-Avance-Corp/app/src/data/inversionistas-queries.ts`

Lines:
`01-lecturas.sql:14-16, 244, 351-352, 376-377, 419-420`; `inversionistas-queries.ts:14-18`

Problem:
Every list/ficha/cuentas/documento RPC inserts a `cartera_lecturas` row, and that table has an `after insert` trigger into the CRM audit log. The client polls all of these on a 15 s interval.

Evidence:
`01-lecturas.sql:15-16` — `create trigger trg_audit_cartera_lecturas after insert ... execute function private.log_audit_crm();`
`inversionistas-queries.ts:14-18` — `lecturaVigente` sets `refetchInterval: 15_000`, `refetchOnWindowFocus: 'always'`, `refetchOnReconnect: 'always'`, and is spread into `useInversionistas`, `useFichaInversionista` and `useCuentasInversionista`.
The document proxy calls the RPC **twice** per download (`handler.mjs:72` and `handler.mjs:81`), producing two `documento` rows per single download.

Impact:
One user with a ficha open and the banking section expanded generates ~12 `cartera_lecturas` rows plus ~12 audit rows per minute, all recording the same access. The table has no retention policy and only a `(actor_id, creado_en desc)` index. Beyond storage growth, this destroys the signal the audit trail exists to provide: a genuine access review cannot distinguish a deliberate consultation from a background poll.

Recommendation:
Log the *first* read of an `(actor, tipo, inversionista)` within a time bucket rather than every RPC (e.g. an `on conflict do nothing` against a unique partial index over a truncated timestamp), or suppress logging on refetches by passing an explicit "deliberate open" parameter. Separately, decide whether the proxy's second descriptor call (`handler.mjs:81`) should log at all — it is a verification, not an access. Add a retention/partition plan and an index on `inversionista_id`.

ARCHITECTURE RISKS:

- A read RPC depending on a write-path function that takes locks (`inversion_persona_contexto`) couples read availability to write concurrency. The comment at `01-lecturas.sql:265-266` acknowledges the lock but scopes the exemption to Directorio only.
- The coverage gate makes cartera availability a global, all-or-nothing property of the entire source corpus. Correct as a safety stance; operationally fragile without an operator view of what is blocking it.
- `cartera_f5_fuentes()` is a full-corpus function invoked on every request path (gate, list, ficha, documento). Every feature added to F5 multiplies this scan.
- The 15 s `refetchInterval` applied uniformly via `lecturaVigente` is the amplifier behind three separate findings (locks, audit volume, bank-panel remounts). Consider whether live revocation needs polling at all, or whether an on-focus + on-action refresh with a longer interval achieves the same guarantee.

SECURITY RISKS:

- The proxy reads Storage with the service-role key (`handler.mjs:73-74`), so the RPC descriptor is the sole authorization boundary for arbitrary object reads within three buckets. The path validation (bucket allowlist, no leading `/`, no empty/`.`/`..` segments, no control chars or backslash, per-segment `encodeURIComponent`, `redirect: 'error'`) is thorough and I found no bypass. This is acceptable, but it means every future change to `inversionista_documento_fn`'s return shape is a security change.
- Third-party PII (cotitular documents) is gated more weakly than the document containing it — P2 #11.
- Directorio scope expansion is plausible in two places (P2 #10, P2 #12); neither is demonstrated, both are cheap to close or to document.
- No secrets, tokens or PII appear in log paths in the attached code. `inversionistas-api.ts:23-24` explicitly avoids sending validator issues to telemetry; `inversion-solicitud-api.ts:52` avoids logging the error body. Good.
- `handler.mjs:43` permits requests with no `Origin`; correct for a Bearer-token API with no cookie auth.

REGRESSION RISKS:

- `descargando` latching (P2 #3) is a live regression in the new screen with no error surface.
- Bank-panel remounting (P2 #4) is a visible regression against the published `CuentasClienteMoneda` behaviour.
- Legacy Avance contract creation remains reachable at `cartera-inversionistas.tsx:81-85`; if that path can create a contract without a canonical `crm.inversionistas` link, it will disable the F5 cartera globally via the coverage gate.
